# Pi 1.6 适配与统计类插件兼容：可执行优化方案

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让 `@llmgates_api/pi-llmgates-provider` 在用户实际运行的 Pi 1.6.1 上类型、行为与统计口径都正确，同时不破坏 0.81.x 基线；固定与 pi-subagents 0.90 / tintinweb 0.26 / pi-subagents-lite 1.20 / pi-lens 的记账边界；门禁通过后才把 peer 上界抬到 `<1.7.0`。

**Architecture:** 不升开发基线（devDependencies 仍是 pi 0.81.1，测试与类型检查继续跑在这一版上）。每处跨版本差异都用"同一份源码同时适配新旧契约"的方式处理：类型从已安装 SDK 派生，compat 字段新旧同发，宽度取新旧算法的较大值。另加一条 CI 兼容通道，在 Pi 1.6.1 上跑生产代码类型检查和全量测试。peer 上界只在 1.6.1 安装包门禁通过后才动。

**Tech Stack:** TypeScript 6.0.3（target ES2022，正则只能用 `u` 标志字面量；`v` 标志只能用 `new RegExp(..., "v")` 运行时构造），vitest 4.1.9，Node ≥ 22.19，`@earendil-works/pi-coding-agent` / `@earendil-works/pi-ai` 0.81.1（基线）与 1.6.1（兼容通道）。

## 0. 审查结论

用户机器上实际运行的是 Pi **1.6.1**，比 `origin/main` 的 peer 上界 `<1.6.0` 高一档，比本地 `HEAD` 的 `<0.87.0` 高得更多。插件在 1.6.1 上能加载，主流程可用，但审查发现下面这些问题：

| 级别 | 问题 | 影响 | Task |
| --- | --- | --- | --- |
| MUST | 终端宽度对印地语、孟加拉语、泰米尔语、缅甸语等文字**少算**（例如 `किताब` 本地算 3，pi-tui 1.6.1 算 5）；对 pi-tui 0.81 的退化簇也有少算 | 少算是崩溃方向：一行被本插件认为够窄，pi-tui 却判定超宽，渲染器会直接抛错（`/endpoint`、`/endpoint-setting` 选择器） | 1 |
| MUST | `provider.stream/streamSimple` 参数类型写死为 `Context`，pi-ai ≥0.86 的契约是 `TranscriptContext` | 在 1.6.1 上类型检查失败（TS2345）；运行时没问题，因为 Pi runtime 会先 `normalizeContext` | 2 |
| MUST | Kimi K3 只下发旧字段 `deferredToolsMode`。pi-ai **0.86.0 起**删掉了它，改用 `supportsMidConvoSystemMessages` + `supportsMidConvoToolAdditions` | 在 1.6.1 上类型检查失败（TS2353）。运行时在 0.86–1.6.x 上，经网关的 K3 退回"每次加工具都改顶层 tools、中途 system 合并进首条"：结果正确，但 prompt cache 前缀会频繁失效 | 3 |
| MUST | `BUILTIN_PROVIDER_IDS` 缺 1.6.1 新增的内置 provider：`azure`、`baseten`、`meta`、`qwen-token-plan-individual`、`qwen-token-plan-individual-cn`、`typesafe` | 新登录可以占用这些 id，遮蔽 Pi 内置 provider。**但不能直接加进现有集合**：现有集合在加载时也会校验，已存这些 id 的老用户会整套网关注册失败，连 `/logout` 都没法用 | 4 |
| MUST | 6 处测试写死了 0.81.1 的数据或签名 | 兼容通道无法变绿，后续每次升级 pi 都会被误报 | 5 |
| SHOULD | 现代 usage 入口（嵌套工具池、`type:"usage"` 条目）只对 SDK `1.0.4/1.2.0/1.5.0` 打开 | 在 1.5.1、1.5.2、1.6.0、1.6.1 上这两条入口关闭，All 少记嵌套工具与独立 usage。这四版的会话条目形状已逐版核对，与 1.5.0 一致 | 6 |
| SHOULD | pi-subagents 事件桥的 `pi.events` 处理器没有异常防护 | Pi ≥1.6.0 会把抛错的事件处理器当扩展错误显示在聊天里；记账代码里的一个 bug 会变成每次子代理完成都弹一次错误 | 7 |
| SHOULD | 第三方插件新版本的形状没有测试钉住 | pi-subagents 0.90 的 `children` / `nestedChildren`、pi-lens 的 `usage:{tokens,elapsedMs}` 以后一旦被误读就会重复计费，而现在没有测试拦截 | 8 |
| SHOULD | CI 只跑 0.81.1 基线 | 这次的问题全是手工在最新 pi 上跑出来的，没有自动化手段 | 9 |
| MUST（发布前） | 文档、门禁清单、peer 上界 | 用户已经在 1.6.1 上运行，但 peer 不覆盖；文档里 peer 的描述前后不一致（`<0.87.0` / `<1.6.0`） | 10、11 |

**已核对、确认无需改动：**

- `catalog-store.ts` 同时适配了 `context.store`（旧）和 `stored + publish`（0.84+）两套刷新契约。
- `input-history.ts` 没有修改 `render()` 的返回值，所以 1.6.0 的 `readonly string[]` 变化与它无关。1.6.1 的 `addToHistory` 改为"移动已有条目"而不是重复追加，正好符合"从旧到新预填"的预期，只需在门禁里实测（Task 11）。
- 1.6.1 的 `registerNativeProvider` 遇到同 id 时，扩展 provider 会覆盖内置 provider，不会抛错。这是 Task 4"加载放行"方案的前提。
- `before_agent_start` 在 Pi ≥1.2 也会为 custom message 的 `triggerTurn` 唤醒触发。TPS 把它算作新一轮，子代理费用仍归启动轮（`origin/main` 的 `588e66a` 已有测试），不需要改。
- pi-subagents 0.90 的 `task:subagent:lifecycle` 载荷只有 `{id,status,agent,description,mode,success?}`，不带 usage。本插件本来就不订阅它，不存在重复计费。
- tintinweb 0.26.3 仍然只发 `subagents:completed` / `subagents:failed` / `subagents:usage`，现有 coverage-only 探测继续生效。
- pi-subagents-lite 1.20 的工具结果没有顶层 `usage`，仍是缺口，同样不存在重复计费。
- pi-lens 4.5.2 不是统计插件。它的 `usage:{tokens,elapsedMs}` 不含 token 计数字段，`extractToolResultUsage` 返回 `[]`（Task 8 用测试钉住）。
- 1.6.1 的 `openai-completions` 只对 OpenAI 官方主机默认用 `developer` 角色（上游 #10741），网关上的通用推理模型改用 `system`。这对网关兼容性更好，本插件不需要覆盖。

```ts
function couldBeWideEmoji(segment: string): boolean {
	const cp = segment.codePointAt(0);
	return (
		(cp !== undefined && cp >= 0x1f000 && cp <= 0x1fbff) ||
		segment.includes("\uFE0F") ||
		(segment.length > 1 && pictographicRegex.test(segment))
	);
}

/**
 * pi-tui (>= 1.6) gives spacing marks a cell each, with or without a base, and
 * counts the visible code point after a mark inside one Indic/Myanmar grapheme.
 * Mirrors its `terminalSpacingMarkRegex` / `clusterWidth` with `u`-flag syntax
 * (ES2022 target): Spacing_Mark minus U+1734/U+302E/U+302F, plus its extras.
 */
const terminalSpacingMarkRegex =
	/^(?:(?![\u1734\u302E\u302F])\p{Mc}|[\u065F\u0F7F\u102B\u102C\u1031\u1033-\u1035\u1038\u103A-\u103E])+$/u;
const markCharRegex = /^\p{Mark}$/u;
const nonPrintingCharRegex =
	/^[\p{Default_Ignorable_Code_Point}\p{Control}\p{Format}\p{Mark}\p{Surrogate}]$/u;
const leadingNonPrintingRegex =
	/^[\p{Default_Ignorable_Code_Point}\p{Control}\p{Format}\p{Mark}\p{Surrogate}]+/u;
const pictographicRegex = /\p{Extended_Pictographic}/u;
/** `v`-flag property of strings; built at runtime because the TS target is ES2022. */
const rgiEmojiRegex: RegExp | undefined = (() => {
	try {
		return new RegExp("^\\p{RGI_Emoji}$", "v");
	} catch {
		return undefined;
	}
})();

function codePointCells(cp: number): number {
	return isWideOrFullwidth(cp) ? 2 : 1;
}

function clusterVisibleWidth(segment: string): number {
	const base = segment.replace(leadingNonPrintingRegex, "");
	const cp = base.codePointAt(0);
	if (cp === undefined) return 0;
	let width = codePointCells(cp);
	let followsMark = false;
	for (const char of [...base].slice(1)) {
		if (terminalSpacingMarkRegex.test(char)) {
			width += 1;
			followsMark = false;
		} else if (markCharRegex.test(char)) {
			followsMark = true;
		} else if (!nonPrintingCharRegex.test(char)) {
			const next = char.codePointAt(0)!;
			if (followsMark || (next >= 0xff00 && next <= 0xffef)) width += codePointCells(next);
			else if (next === 0x0e33 || next === 0x0eb3) width += 1;
			followsMark = false;
		}
	}
	return Math.max(width, legacyClusterWidth(segment, cp));
}

/**
 * pi-tui <1.6 (still inside the peer range) scans the whole segment after its
 * first code unit, so a grapheme that starts with a mark counts a trailing AM
 * vowel or fullwidth form twice there.
 */
function legacyClusterWidth(segment: string, baseCodePoint: number): number {
	let width = codePointCells(baseCodePoint);
	for (const char of segment.slice(1)) {
		const next = char.codePointAt(0)!;
		if (next >= 0xff00 && next <= 0xffef) width += codePointCells(next);
		else if (next === 0x0e33 || next === 0x0eb3) width += 1;
	}
	return width;
}

function graphemeVisibleWidth(segment: string): number {
	if (segment === "\t") return 3;
	if (terminalSpacingMarkRegex.test(segment)) return [...segment].length;
	if (zeroWidthRegex.test(segment)) return 0;
	if (couldBeWideEmoji(segment)) {
		return rgiEmojiRegex?.test(segment) ? 2 : Math.max(2, clusterVisibleWidth(segment));
	}
	const width = clusterVisibleWidth(segment);
	return wideScriptRegex.test(segment) ? Math.max(width, 2) : width;
}
```

说明：
- `zeroWidthRegex`、`wideScriptRegex`、`isWideOrFullwidth` 沿用文件里已有的定义，不要改。
- `pictographicRegex` 在 `couldBeWideEmoji` 之后声明也没问题：它只在模块初始化完成后、被调用时才读取。
- 去掉旧规则 `segment.length > 2`：这条规则原本只是"碰巧"把部分印地语簇算宽，现在由簇算法精确处理。

## 5. 自检（Self-Review）

**覆盖性：** 第 0 节每一个 MUST / SHOULD 都对应一个 Task；"已核对无需改动"的项都附了证据；Backlog 写明了不做的原因。

**无占位符：** 每个代码步骤都给出完整代码；每个命令都写明预期结果。唯一依赖人工判断的是 Task 11 Step 1 的门禁实测，这一步本来就必须由人或 Agent 在真实 Pi 上逐条执行。

**类型一致性：**
- `ProviderStreamContext` 只在 `provider.ts` 内部使用。
- `LOGIN_RESERVED_PROVIDER_IDS` 由 `connection.ts` 导出，`provider.ts` 和 `connection.test.ts` 使用。
- `onGap` 的联合类型与 `collector.noteGap(reason: string)` 兼容。
- `KimiK3OpenAICompat` 是 `OpenAICompletionsCompat` 的子类型，`return compat` 不触发多余属性检查。
- `providerContext` 返回 `never`，可以传给任意版本的 `stream*` 参数。

**风险与回退：**
- 宽度：只会多算，不会少算（已全量对拍）。多算的代价是个别行提前截断。
- Kimi：新旧字段从未在同一版本共存（已逐版核对），不会重复发送工具消息。
- 保留 id：已存实例不受影响；唯一可见的变化是新登录不能再用这 6 个 id，`default` 网关的派生 id 会自动加后缀。
